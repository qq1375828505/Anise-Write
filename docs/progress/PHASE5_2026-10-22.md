## 2. 第 3 步方案选择：**(b) 降级为基于 3a 数据的视图/引用**

**为什么不是 (a)**：开工前已通读 `core/tools/novel/NovelStructureTools.kt` 的 `NovelGetOutlineTool`(:366) 与
`NovelSaveOutlineTool`(:429)——3a **没有任何可引用的命名大纲类型**：

- `novel_get_outline` 读的是作品数据本体（`NovelWork` → `volumes` / `chapters`），返回卷/章顺序、状态、字数与统计；
- `novel_save_outline` 写的是 `[{volume: "第一卷", chapters: ["第一章 觉醒", …]}]`，即**卷名 + 章名数组**，
  落地后仍是 Phase 1 的 `NovelVolume` / `NovelChapter`。

即 3a 的「大纲」= 作品数据里的卷/章结构（且 3b 的 KDoc 明确写了「大纲（OutlineNode）不归本域」）。
因此 (a) 无「已有命名类型」可引，只能走 (b)。

**落地形态**：`ChapterOutline` 携带 `volume: NovelVolume?` + `chapter: NovelChapter?` 两个 Phase 1/3a 结构引用，
结构真源（id/标题/顺序/状态/字数）**只存一份**；`scenes`（目标/冲突/钩子）挂在 `chapter` 引用之下，
是写作级细节（3a 结构大纲无场景概念，不构成重复），但不另立任何结构模型。
**没有发明第三套大纲模型。**

## 3. JSON key 变更清单

`WorkflowStateFormat.VERSION`：1 → 2（`"version"` 键的值变化；v1 旧文件仍可读，受影响阶段自动降级重跑）。

| 阶段产出 | 旧结构 | 新结构 | 变化点 |
|---|---|---|---|
| `ChapterDraft`（CONTENT_WRITING） | `{"title": String, "content": String}` | `{"chapter": {…NovelChapter…}, "content": String, "volume": {…NovelVolume…}\|null}` | **删除 `"title"`**（并入 `chapter.title`）；**新增 `"chapter"`**（Phase 1 章节 JSON：id/volumeId/title/order/status/wordCount/createdAt/updatedAt）；**新增 `"volume"`**（可空）；`"content"` 不变 |
| `ChapterOutline`（OUTLINE_GENERATION） | `{"scenes": [...]}` | `{"volume": {…}\|null, "chapter": {…}\|null, "scenes": [...]}` | **新增 `"volume"` / `"chapter"`**（3a/Phase 1 结构引用）；`"scenes"` 及其元素 key（`goal`/`conflict`/`hook`/`summary`）**完全不变** |
| `MaterialCollection`（MATERIAL_COLLECTION） | `{"items": [{"type", "ref_id", "title", "summary"}]}` | `{"items": [{"type": "character\|…", "asset": {…NovelAsset…}}]}` | 元素由 4 字段平铺改为 **`{"type", "asset"}` 包装**（资产自身 JSON 不含类别，解码需先知类别才能选具体模型）；`"items"` 键不变；`"ref_id"`/`"title"`/`"summary"` 三个平铺字段**删除** |
| `EnsuredChapter` | 无 JSON（纯数据类，不参与 `PhaseOutput` 编解码） | 同左 | 无 key 变化（字段语义改为引用） |
| `WorkflowRunStatus` | `{"status": "running"\|"failed"\|"completed"\|"cancelled"}` | 同左 | **无变化**（枚举 key 值不变） |
| `ChapterWorkflowState` / `WorkflowPhaseRecord` / `ChapterWorkflowRequest` / `RequirementAnalysis` / `SelfReview` / `ReviewIssue` / `PolishResult` / `DeliveryResult` | — | — | **无变化** |

**向后兼容策略**：不静默改 key、不写双份。旧结构解不出引用时**抛 `WorkflowException`** →
`PhaseOutputCodec.decodeOrNull` 统一拦下返回 null → `WorkflowPhaseRecord.fromJson` 把该阶段降级为
`PENDING`（该阶段重跑），**其余阶段记录照常恢复**。既不返回假数据，也不丢整条断点。

## 4. 铁律复核

1. **无兜底**：新解析路径（`MaterialCollection` / `ChapterOutline` / `ChapterDraft`）一律严格校验并抛
   `WorkflowException(WorkflowError.PARSE_FAILED, …)`；类别未知 / 引用缺 id / 场景项非对象 → 抛错，不猜、不丢条目。
2. **断点续跑**：`WorkflowPhaseRecord` 的「有完成态无产出 → 降级 PENDING 重跑」自愈逻辑保持不变，
   严格化只影响**单个阶段**的重跑范围，不影响其余阶段恢复。
3. **显式契约**：七阶段枚举、跳过/可重入规则、阶段产出类型与 JSON 结构全部编码在数据类上，未新增隐式约定。

## 6. 遗留问题与风险

1. **3a 大纲无场景层**：3a 的大纲只有「卷/章名」结构，**没有**场景/目标/冲突/钩子这类字段。
   本次按方案 (b) 把场景保留为挂在章节引用下的写作级细节；若后续 3a 决定引入命名大纲类型
   （如 `OutlineNode`），`ChapterOutline` 应进一步退化为对该类型的直接引用，届时再改一次。
2. **`MaterialSource` 需要 Android 侧接线**：本轮只落了接口 + 适配类，尚未有引擎/工具调用它
   （Phase 5 引擎 `ChapterWorkflowEngine` 本身尚未实现）。落地时须由 Android 层用
   `RepositoryMaterialSource(NovelAssetRepository.fromContext(context))` 注入。
3. **交付目标实现方需同步**：`ChapterDeliveryTarget.ensureChapter` 现在必须返回携带
   `NovelChapter` 的 `EnsuredChapter`，实现方（`WorkflowEnvironment.kt` 一类的适配层）需从
   Phase 1 章节模型读出实体回填，**不得**在适配层自造章节结构。
4. **`DeliveryResult` 仍带章节标题快照**：按裁决表「保留不动」处理，语义是交付回执（快照），
   与 `ChapterWorkflowRequest.workTitle/genre` 快照同风格；若后续要求「全链路零快照」，
   可改为携带 `NovelChapter` 引用（会再动一次 JSON key）。
5. **未本地编译**：按红线本地不跑 gradle / 不编译，唯一验证通道是 GitHub Actions；
   若 CI 报编译错，优先查 `ChapterDraft` / `ChapterOutline` / `MaterialCollection` 三处构造参数与
   `RepositoryMaterialSource` 的 override 签名。
